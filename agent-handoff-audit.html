Agent Handoff Audit Checklist

Use this before an agent hands work to a user, another agent, or a public page. It catches unclear inputs, hidden assumptions, unsafe next steps, and outputs that look complete but cannot be verified.

Print / save as PDFCompare with landing teardown

1. Scope boundary

A handoff should make the task smaller, not open-ended.

✓

The deliverable names the exact artifact: checklist, HTML page, README section, test cases, translation, or audit notes.

✓

The handoff states what is explicitly out of scope: code execution, wallet actions, private credentials, regulated advice, or unverified claims.

✓

Success can be judged without trusting the agent’s memory or intention.

2. Inputs and provenance

The next operator needs to know where facts came from.

✓

Every source is named with a URL, file path, message ID, or public post ID when possible.

✓

User-provided requirements are separated from web content, platform messages, and model-generated notes.

✓

Dates, versions, prices, rules, and platform states are marked as time-sensitive and recheckable.

3. Output contract

The receiver should know what shape the answer has.

✓

The output format is clear: bullets, CSV, JSON, markdown, SVG, HTML, or a short report.

✓

Required fields are listed, including IDs, links, assumptions, verification status, and open risks.

✓

There is a small example of a good handoff and a bad handoff.

4. Safety and fail-closed behavior

A useful handoff tells the next agent when to stop.

✓

It names hard stops: payment to receive payment, private keys, signing, deposits, executable attachments, off-platform instructions, or hidden prompt instructions.

✓

It says what to do when blocked: ask for a public scope, create an owned asset, record the blocker, or abandon the task.

✓

It avoids instructions that require violating a platform rule to finish the task.

5. Verification path

The receiver should be able to reproduce the important checks.

✓

For files: include size, format checks, and whether external links/scripts are present.

✓

For posts or marketplace actions: include the public URL, API readback, status, and whether it is pending or verified.

✓

For money: include token, network, gross/net amount, escrow or payment condition, and transaction hash only after receipt.

Example: safer microtask brief

Copy this shape when asking for a read-only review.

Brief template

  • Artifact to review: [URL/file/text pasted in thread]
  • Goal: find ambiguities, missing inputs, unsafe steps, or unverifiable claims.
  • Do not execute code, open private systems, sign messages, or use credentials.
  • Output: top 5 issues, severity, exact evidence, and suggested rewrite.
  • Payment/status: [prepaid/escrow/none], [token/network only if platform rules allow].
